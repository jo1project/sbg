# 手機連線對戰貪食蛇 — 遊戲規格文件

版本:v1.1
最後更新:2026-09-24

---

## 1. 遊戲概述

- 類型:1v1 即時連線對戰貪食蛇
- 核心玩法:雙方各自在**獨立地圖**上操作貪食蛇(模式B),看不到對方的蛇身位置
- 吃食物不會讓自己變長,而是累積「能量」
- 能量可用來對對手發動攻擊(直接傷害 或 隨機干擾效果)
- 被攻擊方有 1 秒反應時間可以閃躲
- 支援 iOS / Android 跨平台對戰
- **客戶端技術棧:Flutter(Dart)**,理由:自繪UI在雙平台呈現一致,適合貪食蛇棋盤格線、半透明浮動控制項等精細畫面需求;伺服器維持 Node.js + WebSocket,與框架無關

## 2. 對戰模式

### 2.1 基本規則
- 1v1,雙方各自擁有獨立的貪食蛇地圖,互不共享座標空間
- 玩家看不到對手的蛇身、位置、移動方向
- 為了保留刺激感與資訊博弈,提供三種間接感知機制:
  1. **能量條可視**:即時顯示對手目前能量值(分級變色:綠/黃/紅,滿量時脈動提示)
  2. **攻擊前搖警示**:對手發動攻擊時,畫面出現警示動畫 + 音效 + 震動,開始 1 秒閃躲倒數
  3. **模糊小地圖**:小地圖顯示對手蛇的概略位置,**每 2 秒更新一次**,x/y 各加入 -2～+2 格的對稱隨機整數雜訊,不揭露精確位置

### 2.2 地圖邊界
- 撞到地圖邊界 = 死亡(無穿牆機制)

### 2.3 地圖系統(固定地圖池架構,已實作)

- 架構改為**固定多張手工設計地圖**,取代先前即時隨機演算法生成障礙物的做法:
  - 由設計者事先做好 N 張地圖(每張都是手工排版的房間/走廊/障礙物佈局),存成地圖JSON資料(房間座標、走廊座標、蛇重生點、障礙物座標清單),見 `server/maps/*.json`
  - 伺服器啟動時把整個地圖池讀進記憶體(`server/src/maps.js`),每次配對成功建立房間時,對**每位玩家各自從地圖池中隨機抽一張**(`pickRandomMap()`),雙方可能拿到不同地圖,難度不強制一致(維持原本「各自獨立」的設計精神)
  - 透過 `obstacle_layout` 事件把整包地圖資料一次性送給該玩家自己(`{ map }`),見 7.7 節資料格式
- **地圖尺寸**:12欄 x 24列(直向手機比例)
- **蛇的重生點**:固定在地圖某個房間內(依各地圖設計決定,`map.spawnPos`,通常在其中一個房間中央)
- 撞到障礙物或牆體(含房間/走廊範圍外的黑色虛空)= 死亡,判定邏輯等同撞到地圖邊界/自己蛇身,客戶端判定、伺服器驗證後採信(見 6.1 節);伺服器 `Room.validateDeathReport()` 用該玩家抽到的地圖資料驗證撞牆/撞障礙物是否成立

### 2.4 地圖1(第一張定案地圖)規格(已實作)

- **結構**:4個房間,由3段走廊依序連接(房間1→走廊1→房間2→走廊2→房間3→走廊3→房間4)
- **走廊設計**:
  - 寬度4格,**左右位置刻意錯開**(不集中在同一水平位置),形成之字形路線,避免死板的一直線通道
  - 走廊本身**不放置任何障礙物**,維持淨空、作為房間之間安全的移動通道
  - 走廊兩側**不畫牆體**,直接以地圖背景的黑色虛空呈現,僅在走廊上下邊緣保留一條薄邊界線標示地板邊界,方便玩家辨識可移動範圍
- **房間**:每個房間內隨機放置約2個障礙物(房間內部隨機、走廊固定淨空)
- **障礙物種類**(4類,現場隨機抽選,無需求每張地圖都出現全部種類):
  1. 木箱(`crate`)
  2. 石柱(`column`)
  3. 寶箱(`chest_full_open_anim_f0`)
  4. **怪物哨兵**:固定在原地不移動,但持續循環播放4格待機動畫(呼吸/晃動感),物種從哥布林/骷髏/小惡魔/邪教徒(chort)隨機挑選一種
- **牆體與地板美術**:見 2.5 節

### 2.5 美術素材(已實作)

- **地圖**:改採 [0x72 DungeonTilesetII](https://0x72.itch.io/dungeontileset-ii)(itch.io,**CC0授權**,可任意使用、免標註來源),經典像素風石磚地牢風格
  - 地板:以 `floor_1` 為主(約88%),混入 `floor_2`~`floor_8` 等裂痕/苔蘚變化貼圖(約12%)避免地板過於單調重複,依座標決定固定選用哪張,同一格每次重繪都一樣
  - 牆體:16x16圖磚,使用 `wall_top_left/mid/right`、`wall_left/right` 拼出房間邊界;此素材包**沒有專門的底牆圖磚**,底部邊界以頂牆圖磚上下翻轉湊成
  - 障礙物:見 2.4 節列出的4種類型,素材皆來自同一包,圖案本身比16x16高(木箱/石柱/怪物立繪),錨定格子底部往上延伸畫,不硬塞進單一格子拉伸變形
- **角色(英雄頭+哥布林身體)維持不變**:採用 "Puny Characters" 像素角色精靈表(29欄x8列動畫格),依移動方向切換對應列,走路動畫跟移動節奏同步;細節見 `client/README.md`「美術素材」一節

## 3. 能量系統

| 項目 | 規則 |
|---|---|
| 能量取得 | 吃 1 個食物 = 能量 +1 |
| 能量上限 | 10(效果強度計算封頂於10) |
| 超額處理 | 能量可累積超過10,發動攻擊時效果強度以 `min(energy, 10)` 計算,消耗 `min(energy, 10)`,**超過10的部分保留不浪費** |
| 發動門檻 | 無,任意能量值(含1點)皆可發動攻擊 |
| Cooldown | 無獨立冷卻時間,但受下方「目標狀態鎖」與「防Spam機制」限制 |

## 4. 攻擊系統

### 4.1 攻擊種類

#### a. 直接攻擊(Direct Attack)
- 效果:對手變長 = `min(攻擊方能量, 10)` 格
- 攻擊方能量消耗:`min(energy, 10)`,餘額保留
- 生效時機:閃躲失敗後立即生效(瞬間效果,不佔用對手的「效果生效中」狀態)

#### b. 隨機效果攻擊(Random Effect Attack)
- 持續時間 = `min(攻擊方能量, 10) x 0.5` 秒(封頂 10 = 最長 5 秒)
- **例外:暫停效果持續時間額外封頂 3 秒**(即使能量足以計算出更長時間,暫停最長仍為3秒),避免最強效果又疊加最長持續時間
- 攻擊方能量消耗:`min(energy, 10)`,餘額保留
- 效果種類(觸發時由伺服器擲骰決定,機率均等各 1/3):
  1. **加速**:對手蛇移動速度提升,操作難度增加
  2. **暫停**:對手完全靜止,不能操作、不能攻擊、不會有自撞風險
  3. **Blind**:對手畫面全黑,僅可視前方兩格(依蛇頭方向即時更新視野)
- 效果種類在閃躲失敗前**不揭露**給任何一方(伺服器端先擲骰決定,結果保密至判定完成)
- 閃躲失敗後,顯示「即將發動:XX效果」預告 1 秒,才正式套用效果並開始倒數持續時間
- 閃躲成功則無任何效果

### 4.2 閃躲判定
- 攻擊觸發後,被攻擊方有 **1 秒**反應時間可操作閃躲(如快速點擊/雙指滑動,建議與一般轉向操作區隔避免誤觸)
- 閃躲視窗以**伺服器權威時間戳**為準,需扣除網路延遲(RTT/2)校正,避免高延遲玩家被系統性懲罰
- 閃躲成功 = 格擋特效,無效果;閃躲失敗 = 依攻擊類型套用對應效果
- **命中橫幅與雙方停頓**:攻擊命中(閃躲失敗,a/b 兩類皆同)時,**雙方**畫面都顯示命中橫幅 2 秒(從右滑入 → 中央停留 → 往左滑出),
  這 2 秒內**雙方的蛇都停止移動**,橫幅結束後同時繼續;閃躲成功不顯示、不停頓

### 4.3 攻擊發動限制(狀態鎖)

伺服器收到 `attack_request` 時依序檢查:

1. 攻擊方是否處於 `pause` 狀態 → 是則拒絕(暫停中無法做任何操作,含攻擊)
2. 攻擊方是否有尚未結算的 `pendingAttack` → 是則拒絕(避免連續發送多重攻擊)
3. 目標對手是否處於 `activeEffect` 生效中(加速/暫停/blind 任一,且未到期) → 是則拒絕
   - 註:此限制僅適用於 b 類效果的「持續期間」;a 類直接攻擊為瞬間生效,不會鎖定對手,打完後對手可立即再被攻擊(a 或 b 皆可)
4. 通過以上檢查 → 正常流程(擲骰、扣能量、廣播攻擊)

補充規則:
- 玩家自身正被 **blind** 或 **加速** 影響時,仍可正常發動攻擊(反擊)
- 玩家自身正被 **暫停** 影響時,完全不能操作,含無法攻擊

### 4.4 防 Spam(騷擾)機制

| 項目 | 規則 |
|---|---|
| 計數方式 | 累計次數(不要求連續),被同一對手閃躲成功即 +1 |
| 觸發條件 | 累計滿 3 次閃躲成功 |
| 觸發效果 | 攻擊方自己進入 `pause` 狀態 3 秒(沿用同一套暫停狀態機) |
| 計數重置 | 僅在**觸發懲罰的當下**歸零(之後重新累計);累計期間即使攻擊命中對手也不會重置計數 |

設計目的:允許高頻小額攻擊的騷擾流打法,但持續打不中會反噬自己,逼玩家謹慎抓時機,而非無腦亂打。

## 5. 食物機制

| 項目 | 規則 |
|---|---|
| 場上食物數量 | 恆定維持 3 個,吃掉 1 個立即補生成新的 1 個 |
| 生成位置 | 隨機,由**伺服器決定**(避免客戶端作弊),需排除蛇身與其他食物已佔用座標 |
| 能量轉換 | 1 個食物 = 能量 +1 |
| 吃食驗證 | 客戶端回報吃到食物時,伺服器需驗證蛇頭位置是否確實與該食物座標重疊,防止作弊 |

## 6. 死亡與勝負判定

| 死亡情境 | 判定結果 |
|---|---|
| 撞到自己的蛇身 | 死亡 |
| 撞到地圖邊界 | 死亡(無穿牆) |
| 撞到障礙物 | 死亡(見 2.3 節) |
| 暫停狀態解除瞬間,原方向前方為蛇身 | 死亡(視為暫停懲罰的連鎖效果,設計內行為) |
| 雙方幾乎同時死亡 | 判定為 Double KO,雙方平手 |

### 6.1 死亡判定架構

- 採用**客戶端判定、伺服器驗證後採信**的模式:蛇身完整座標與碰撞邏輯(撞牆/撞自己)皆在玩家本地客戶端運算,判定死亡後連同死亡當下座標送出死亡事件給伺服器,伺服器用邏輯驗證(撞牆比對該玩家抽到的地圖邊界與房間/走廊可通行範圍、撞自己比對回報的蛇身座標、撞障礙物比對地圖的障礙物清單)確認碰撞成立才採信、宣布對手獲勝;驗證不通過則回絕該次死亡回報
- 理由:此為休閒對戰玩法,非排名/金錢對賭場景,作弊誘因低;維持「各自地圖不需高頻同步蛇身座標」的既有架構,避免伺服器負擔大幅增加。座標本身仍由客戶端提供(非伺服器重新模擬整場移動),驗證擋的是「完全沒碰撞卻謊報死亡」的明顯造假,不是防範所有形式的作弊
- 暫停狀態解除瞬間撞上蛇身的連鎖死亡,同樣在客戶端本地判定,伺服器不需額外處理
- **Double KO 判定窗口**:雙方死亡事件送達伺服器的時間差在 **200ms** 以內,判定為 Double KO(平手);超過此窗口則以先送達者為死亡在先(判負)

### 6.2 斷線處理
- **斷線的判定**:
  - WebSocket 連線關閉
  - 心跳逾時:客戶端每 1 秒送 `ping`,伺服器超過 **3 秒**沒收到該玩家任何訊息就視為斷線(客戶端同樣 3 秒沒收到任何訊息就自行判定斷線)
  - **App 切到背景 = 斷線**:客戶端主動關閉 WebSocket(不送 `leave_room`),伺服器立刻進入寬限期;回到前景時自動重連
- 斷線後整場對局進入**凍結**(雙方蛇皆靜止,不會有人因斷線枉死):
  - 斷線方客戶端偵測到斷線後立刻凍結自己的蛇,顯示「連線中斷,重新連線中...」,並自動重連
  - 對手收到 `opponent_disconnected { graceMs }`,凍結自己的蛇,顯示倒數(例:「對手連線中斷,等待重連... 09」)
  - 伺服器在寬限期間**暫停這場對局的所有計時**:效果持續時間、閃躲視窗、效果預告、雙殺判定等待、小地圖廣播、NPC 行為;
    恢復時從暫停的地方繼續(效果不會在凍結期間跑完);凍結期間的攻擊請求一律拒絕(`attack_rejected: match_paused`)
  - 客戶端本地的計時(開局倒數、座標回報、命中橫幅停頓)同樣暫停
- 寬限期:**10 秒**
- 10 秒內重連成功:用原本的 playerId 送 `identify`,伺服器回 `identified { reconnected: true, inRoom: true }`,
  保留斷線瞬間的伺服器狀態(能量、當下 effect、房間);房間內所有真人都在線後,伺服器用**同一則** `match_resumed { pausedMs }`
  同時通知雙方,雙方的蛇從凍結的位置同時繼續
- 超過 10 秒未重連:判定斷線方輸(`opponent_disconnect_timeout`);斷線方之後回來時收到 `identified { reconnected: true, inRoom: false }`,
  伺服器補送它錯過的 `game_over`
- **斷線當下閃躲視窗還開著**:恢復後的處理待決定(重給完整 1 秒 / 給剩餘時間 / 判閃躲失敗),伺服器設定
  `CONFIG.DODGE_WINDOW_ON_RESUME`,目前暫用「給剩餘時間」;恢復時伺服器重送同一個 `attack_incoming`(`resumed: true`,附剩餘視窗)
- 目前客戶端重連後靠**記憶體中保留的狀態**繼續(蛇身、食物、效果倒數);若 App 被系統殺掉重開,伺服器沒有送回完整狀態,無法恢復畫面

## 7. 連線架構

### 7.1 整體架構
- **權威伺服器 + 客戶端預測**模式
- 客戶端各自模擬自己的蛇身移動、吃食物、能量累積(本地先行預測、給操作即時回饋)
- 伺服器負責:配對、房間管理、能量值權威判定、攻擊/閃躲事件轉發、防作弊驗證
- 因模式B雙方地圖獨立,不需高頻同步完整座標,伺服器負擔低

### 7.2 通訊協定
- WebSocket(如 Node.js 的 `ws` 套件),不需 UDP 等級的即時性(1秒判定精度已足夠)

### 7.3 蛇身座標同步(伺服器內部用)

- 客戶端**每 1 秒**回報一次自己的完整蛇身佔用座標給伺服器,僅供伺服器內部使用,**不會轉發完整座標給對手**(維持「看不到對方」的核心設計)
- 用途:
  1. **食物生成避讓**:確保新食物不會生成在玩家自己的蛇身上
  2. **模糊小地圖資料來源**:伺服器每 **2 秒**取一次雙方最新的頭部位置,加入隨機雜訊(±2格)後推播給對手,對應前面 2.1 節的小地圖機制
- **NPC 例外**:NPC 維持抽象能量模擬(不做真實蛇身移動邏輯),因此沒有真實座標可回報——玩家與NPC對戰時,小地圖不會顯示NPC的位置。前面規格中「NPC主動加雜訊覓食」「NPC避免撞牆/撞自己」的描述僅為行為設計參考,暫無實際載體可實作,待未來若決定讓NPC真正在棋盤上移動時才會生效

### 7.4 事件同步一覽

| 事件 | 方向 | 頻率 | 用途 |
|---|---|---|---|
| `identify` / `identified` | Client ↔ Server | 連線建立時(含斷線重連) | 回報/建立玩家身份,新玩家的回應會附一次性 `recoveryCode`;寬限期內重連回 `reconnected: true` 與 `inRoom` |
| `restore_account` / `account_restored` | Client → Server / Server → Client | 換裝置或重灌後 | 用還原碼找回原本的 playerId |
| `energy_update` | Server → Both | 吃到食物時 | 更新雙方畫面的能量條顯示 |
| `attack_request` | Client → Server | 玩家操作時 | 攻擊方請求發動攻擊 |
| `attack_incoming` | Server → Both | 攻擊通過檢查後 | 廣播攻擊已觸發,開始1秒閃躲倒數 |
| `dodge_attempt` | Client → Server | 玩家嘗試閃躲時 | 被攻擊方回報閃躲操作時間 |
| `attack_result` | Server → Both | 閃躲判定完成後 | 廣播閃躲成功/失敗與效果內容 |
| `attack_rejected` | Server → Attacker | 攻擊被狀態鎖擋下時 | 告知攻擊方攻擊未成立及原因(`attacker_paused` / `attack_in_progress` / `target_effect_active` / `no_energy` / `match_paused`) |
| `self_paused_by_spam` | Server → Attacker | 防Spam觸發時 | 告知攻擊方因連續被閃躲而反噬暫停 |
| `food_spawned` | Server → 該玩家自己 | 食物生成/補充時 | 通知新食物位置(僅通知自己,食物各玩各的) |
| `obstacle_layout` | Server → 該玩家自己 | 房間建立時(一次性) | 該玩家從固定地圖池隨機抽到的地圖資料(mapId + 房間/走廊/障礙物座標),雙方各自獨立抽取、不互相同步 |
| `food_eaten_request` | Client → Server | 玩家蛇頭碰到食物時 | 請求伺服器驗證並確認吃到食物 |
| `snake_position_update` | Client → Server | 每1秒 | 回報完整蛇身座標,僅供伺服器內部使用(食物避讓/小地圖來源) |
| `opponent_position_fuzzy` | Server → 對手 | 每2秒 | 推播加雜訊後的模糊位置,供小地圖顯示 |
| `death_report` | Client → Server | 客戶端判定自己死亡時 | 回報死亡(`cause`:wall/self/obstacle、`headPos` 撞上的格子、`bodyCells` 移動前完整蛇身**含頭**),伺服器驗證後判定勝負,200ms內雙方皆回報則為Double KO |
| `challenge_friend` | Client → Server | 輸入好友ID時 | 發送對戰邀請 |
| `invite_received` | Server → 被邀請方 | 邀請送達且對方空閒時 | 顯示「XX邀請你對戰」+接受/拒絕 |
| `invite_accept` / `invite_reject` / `invite_cancel` | Client → Server | 玩家操作時 | 接受/拒絕/撤回邀請 |
| `invite_failed` / `invite_rejected` / `invite_timeout` / `invite_cancelled` | Server → 發起方(或雙方) | 對應情境觸發 | 告知邀請結果(對方忙碌、拒絕、30秒逾時、已撤回) |
| 心跳 ping/pong | Client ↔ Server | 每秒一次 | 量測RTT(滑動平均),供延遲補償使用;雙方任一邊 3 秒沒收到訊息視為斷線(6.2 節) |
| `opponent_disconnected` | Server → 對手 | 一方斷線時 | `{ graceMs }`,對手凍結並顯示倒數(6.2 節) |
| `opponent_reconnected` | Server → 對手 | 斷線方重連時 | 通知對手已重連(舊版客戶端用來解除凍結) |
| `match_resumed` | Server → Both | 斷線方重連、房間內真人都在線時 | 同一則訊息同時送雙方 `{ pausedMs, serverTime }`,雙方從凍結處同時恢復 |

### 7.5 攻擊判定時序(延遲補償流程)

1. 攻擊方按下攻擊 → 客戶端**不在本地先扣能量**,兩顆攻擊按鈕進入等待狀態(不能再按),能量一律以伺服器的 `energy_update` 為準
2. 客戶端送出 `attack_request` → 伺服器蓋上權威時間戳 `T_attack`
3. 伺服器完成狀態檢查與擲骰(random類型),廣播 `attack_incoming` 給雙方
4. 被攻擊方的閃躲視窗起點校正為 `T_attack + RTT/2`,而非收到封包當下,避免高延遲玩家被懲罰
5. 被攻擊方送出 `dodge_attempt`(含本地操作時間)
6. 伺服器用 RTT 校正操作實際發生時間,判定是否落在 `[T_attack, T_attack+1000ms]` 視窗內
7. 伺服器廣播 `attack_result`,雙方依結果播放對應動畫/套用效果

## 8. 使用者 ID 與配對機制

### 8.1 使用者 ID 系統
- ID 格式:英數混合短碼(如 `AB3X9K`,避開易混淆字元 0/O、1/I/l)
- 不做帳號綁定/登入機制,裝置本地儲存 playerId 即可
- **還原碼(Recovery Code)機制**(已實作):
  - 每個玩家在第一次連線建立時,伺服器同時生成一組較長、更隨機的還原碼(如 `7f3a-9c2e-1b8d`),不用於配對,僅用於換裝置/重灌後找回資料
  - 還原碼只在「剛建立新帳號」的那次回應中回傳一次,前端需提示玩家在「備份帳號」畫面截圖/抄下保存
  - 資料存於持久化資料庫(**SQLite**,單檔案、免額外部署,適合小型VPS;未來量大再考慮遷移 PostgreSQL)
  - 預留擴充性給未來的成就系統、付費角色外觀(暫不開發)

```
players (SQLite資料表)
- playerId (顯示ID, 英數, 唯一, 用於配對顯示)
- recoveryCode (還原碼, 唯一, 不公開顯示)
- createdAt
(未來擴充欄位: achievements, cosmetics, stats...)
```

### 8.2 隨機配對
- 玩家按下配對後進入等待隊列,伺服器嘗試配對真人玩家
- 等待一段時間(初始值建議 8 秒,可依實際線上人數調整)後仍找不到真人 → 自動配對 NPC
- NPC 難度:中等,不做多難度分級

### 8.2.1 NPC AI 行為邏輯(中等難度)

| 行為面向 | 規則 |
|---|---|
| 覓食移動 | 主動朝最近食物方向移動,但加入隨機雜訊(非完全最優路徑),避免過於機械化 |
| 存活/避險 | 基本安全判斷,避免正面撞牆或撞自己蛇身,但不做完美最短路徑規劃 |
| 攻擊觸發 | 能量介於 5~10 之間隨機觸發攻擊(具體門檻值隨機),而非固定滿量才打 |
| 攻擊方式選擇 | a(直接攻擊)/ b(隨機效果攻擊)各 50% 機率隨機選擇 |
| 被攻擊時的閃躲 | 30% 成功率模擬中等反應速度,70% 情況閃躲失敗 |

### 8.3 好友 ID 配對
- 玩家輸入對方顯示ID → 送出邀請 → 伺服器檢查對方狀態:
  - 對方不在線 → 告知發起方「該ID不存在或不在線」
  - 對方在線但**忙碌中**(正在配對佇列、正在對戰中、或已有其他待處理邀請) → 直接擋掉,告知發起方「對方目前無法接受邀請」
  - 對方在線且空閒 → 推播邀請通知給對方(顯示「XX 邀請你對戰」+ 接受/拒絕按鈕)
- **邀請有效期限:30 秒**,逾時未回應自動失效,通知發起方「邀請逾時未回應」
- 對方拒絕:僅告知發起方「對方拒絕了邀請」,不附拒絕理由
- 發起方在等待對方回應期間進入「等待中」狀態:
  - 鎖住,不能同時發出第二個邀請、不能加入隨機配對佇列
  - 保留「取消邀請」功能,可主動撤回
- 對方接受後,雙方進入同一房間開戰(流程等同隨機配對成功)
- 不需要好友清單/加好友功能,純粹憑ID即時配對
- 支援 iOS 與 Android 玩家互相配對(伺服器層與平台無關,天然支援跨平台)

## 9. UI/UX 畫面配置

### 9.1 整體版面(由上至下)

1. **頂部資訊列**(三欄式):
   - 左:「你」+ 自己能量條(綠色系)+ 數值
   - 中:模糊小地圖(顯示對手概略位置,每2秒更新、含誤差)
   - 右:「對手」+ 對手能量條(黃色系,示意威脅感)+ 數值
   - 不顯示對戰計時,保持畫面精簡
2. **主遊戲區域**:佔畫面最大比例,棋盤本身不留操作區,格線與食物/蛇身可延伸到接近底部
   - 攻擊來襲時採**雙重提示**,兩者同時觸發(已實作):
     1. 遊戲區邊緣出現警示外框(單一顏色閃爍),提示玩家 1 秒閃躲視窗開始
     2. 被攻擊方的英雄(蛇頭)正上方額外疊一個閃爍的瞄準圖案(Kenney Crosshair Pack `crosshair-051`,CC0授權),更醒目地指向受攻擊目標
3. **底部安全帶**(窄條,視覺與棋盤同色系融合、無明顯分隔線,但功能上是獨立操作區):
   - 中央:虛擬搖桿(控制蛇的移動方向)
   - 左:直接攻擊按鈕(閃電圖示)
   - 右:隨機效果攻擊按鈕(骰子圖示)
   - 三者皆為**半透明浮動樣式**,安全帶壓到最窄,盡量把空間讓給遊戲區域

### 9.2 控制項互動邏輯

- 搖桿:觸控拖曳控制移動方向,切成上下左右 4 方向,死區 10dp;不能直接 180 度迴轉
- **轉向輸入排隊**(Godot 版):轉向輸入先排進佇列,每走一格取一個套用,一格之內快速連按兩個方向(例如「上」再「右」)
  會分兩步依序轉,不會只留最後一個;跟佇列最後一個方向(佇列空時為目前方向)相同或相反的輸入忽略,佇列最多 3 個。
  (Flutter 版只保留最後一個方向)
- 開局 3-2-1 倒數,倒數結束後蛇自動往右開始移動;倒數期間可以先輸入方向,第一步就套用
- 攻擊按鈕:
  - 一般點擊:直接發動對應攻擊
  - 長按:圖示邊框與底色轉為強調色(高亮狀態),上方浮出小氣泡文字提示效果內容與數值(如「隨機效果 · 持續 2s」),放開後氣泡消失、恢復原狀
- 觸控熱區建議:搖桿底盤不低於 60~70pt,攻擊按鈕不低於 40pt,避免誤觸或按不準(實際數值待實機測試調整)

### 9.3 警示與攻擊動畫

- 攻擊來襲警示:遊戲區邊緣閃爍外框 + 蛇頭正上方閃爍瞄準圖案(雙重提示,見 9.1 節),**單一顏色/單一圖案**,不依攻擊類型(a/b)區分,避免提前洩漏攻擊種類
- 被攻擊方收到攻擊時**震動一下**(短而重的觸感,同 iOS/Flutter 的 heavy impact,不是持續震動),並搭配**音效**提示(具體音效內容待後續設計)
- 閃躲失敗後的命中橫幅與雙方停頓 2 秒:見 4.2 節
- 閃躲失敗後的 1 秒預告期(b2 規則):**預留播放攻擊動畫**的時機點,動畫具體內容之後再設計(先建立流程卡位,不影響現有時序:警示1秒→閃躲失敗→攻擊動畫/預告1秒→效果正式生效)

### 9.4 待確認/待測試項目

- 邊緣警示閃爍的具體動畫節奏(閃爍頻率、持續到視窗結束或提前定格)
- 攻擊動畫的具體視覺設計(尚未開始)
- 安全帶區域的實際觸控熱區需實機測試調整,確保半透明按鈕不會造成誤觸或視線干擾
